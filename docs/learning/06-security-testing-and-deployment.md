# DishReview 学习文档：阶段 6——安全、测试与部署

---

## 1.认证与授权

### 1.1 当前登录机制

当前项目没有引入 Spring Security，而是使用两个 Spring MVC 拦截器：

1. `RefreshTokenInterceptor` 顺序为 0：读取 `authorization` 请求头，从 Redis Hash 恢复 `UserDTO` 并刷新 TTL。
2. `LoginInterceptor` 顺序为 1：检查 `UserHolder` 是否有当前用户。
3. 请求结束后清理 ThreadLocal，避免 Tomcat 线程池复用时出现用户串号。

```text
authorization Token
  -> Redis login:token:{token}
  -> UserDTO
  -> UserHolder(ThreadLocal)
  -> LoginInterceptor
  -> Controller / Service
  -> afterCompletion 清理
```

### 1.2 公开接口与需要登录的接口

`MvcConfig` 显式排除了部分公开接口：

- 登录和验证码；
- 热门博客；
- 店铺查询和店铺类型；
- 优惠券查询。

新增、修改、上传和秒杀等接口没有被排除，默认需要通过登录拦截器。

学习时要检查两件事：

1. 路径排除是否过宽，例如不能为了让一个 GET 查询公开，就把整个资源路径都放开；
2. “登录了”不等于“有权限操作任何资源”，后续还需要区分普通用户、商家和管理员的权限。

### 1.3 当前授权的局限

当前主要是“是否登录”校验，没有看到完整的角色、资源所有权和管理员权限模型。例如：

- 已登录用户是否都能新增店铺；
- 已登录用户是否能修改任意店铺；
- 用户是否只能删除自己上传的图片；
- 是否存在管理员专属接口。

面试时可以把它描述为：当前实现完成了基础会话认证和部分接口保护，但细粒度授权仍是后续完善方向。

## 2.Token 与密码安全

### 2.1 Token 生命周期

登录成功后，项目把脱敏后的 `UserDTO` 以 Hash 存入 Redis，并设置有限 TTL。每次携带有效 Token 的请求都会刷新 TTL，登出时删除对应 Redis Key。

需要关注：

- Token 不应写入日志、截图或提交到 Git；
- Redis 中不应存储密码；
- Token 失效应该能被服务端主动撤销；
- Token TTL 应符合业务安全和用户体验要求；
- 多设备登录、单点登出和 Token 轮换尚未形成完整策略。

### 2.2 当前密码编码实现

`PasswordEncoder` 当前是“随机盐 + MD5(password + salt)”的自定义实现。它具备盐值和校验逻辑，但不等于现代生产级密码哈希方案。

需要明确的判断：

- 加盐可以减少相同密码产生相同摘要的问题；
- MD5 速度很快，不适合抵抗现代密码爆破；
- 密码存储应该使用专门的慢哈希算法，例如 BCrypt、SCrypt 或 Argon2；
- 升级密码算法时要考虑旧密码迁移和登录兼容。

这属于后续安全优化点，不能仅凭当前测试通过就说密码存储已经达到生产安全标准。

## 五、输入、XSS 与文件上传

### 5.1 博客内容的 XSS 防护

发布博客时，`BlogController.saveBlog()` 对标题和内容进行 HTML 转义，把危险标签转换成普通文本，降低存储型 XSS 风险。

理解这段代码时要追问：

1. 是在写入数据库前转义，还是在输出时转义？
2. 前端是否又进行了 HTML 解析？
3. 是否存在其他入口可以写入博客内容？
4. 图片 URL、昵称、评论内容是否也需要相同的输出策略？

当前实现至少覆盖了博客标题和内容，但不能推断整个应用已经完成统一的 XSS 防护。

### 5.2 文件上传防护

`UploadController` 当前包含：

- 空文件校验；
- 5 MB 大小限制；
- 图片扩展名白名单；
- UUID 文件名；
- 二级目录分散文件；
- 删除文件时使用 canonical path 防止路径穿越；
- 删除接口支持 DELETE，同时保留 GET 兼容逻辑。

上传安全的核心目标不是“文件能保存”，而是：

```text
攻击者不能上传可执行文件
攻击者不能写入任意目录
攻击者不能删除上传目录之外的文件
攻击者不能用超大文件耗尽磁盘或内存
```

当前代码仍有需要继续验证的点：

- 只检查扩展名不能完全证明文件内容是图片，生产场景还应检查 MIME、文件头和解码结果；
- canonical path 的边界判断应保证目标路径是真正位于上传目录内，不能只依赖简单字符串前缀；
- 上传目录是硬编码的 Windows 路径，换环境会失败；
- 删除接口兼容 GET 会扩大误操作和 CSRF 风险；
- 当前没有看到文件数量、磁盘配额和恶意内容扫描策略。

## 六、配置、日志与异常处理

### 6.1 配置中的敏感信息

当前 `application.yaml` 使用了环境变量占位符，但仍保留了远程数据库/Redis 地址和默认凭据。环境变量优先并不能抵消默认值泄露风险。

正确的生产配置原则：

1. 仓库中只保留无敏感信息的示例配置；
2. 生产地址、用户名、密码通过部署环境注入；
3. 已经提交过的真实密码应立即轮换；
4. 不把 `.env`、密码、Token 写进报告、截图或提交信息；
5. 测试模式和生产模式必须通过明确配置区分，生产环境不能返回验证码明文。

### 6.2 日志

当前代码已经避免在生产模式日志中直接记录验证码，但测试模式会为了联调返回或记录验证码。学习时要区分：

- 测试方便不等于生产安全；
- 手机号、Token、密码、验证码都属于敏感信息，日志需要脱敏；
- 业务日志应包含足够的请求上下文，但不能包含秘密；
- 异常日志需要能关联请求，却不应把数据库连接信息和凭据打出来。

### 6.3 全局异常处理

`WebExceptionAdvice` 统一捕获 `RuntimeException`，记录错误并向客户端返回通用“服务器异常”。

优点：避免把堆栈直接返回给客户端。

需要继续完善的方向：

- 参数校验异常、业务异常、数据库异常应有不同的错误码；
- 日志中应有请求 ID，便于定位；
- 不应把所有异常都压缩为同一类结果；
- 不应在日志中打印敏感配置或完整请求体。

## 七、当前测试覆盖了什么

仓库当前有两类测试：

### 7.1 Spring 上下文测试

`DishReviewApplicationTests` 使用 `@SpringBootTest`，用于验证 Spring 应用上下文是否能启动。它可能依赖当前配置中的外部 MySQL/Redis，不能自动等同于业务接口测试。

### 7.2 安全修复单元测试

`SecurityFixTests` 不连接外部服务，主要验证：

- 文件扩展名白名单；
- 路径穿越判断；
- 验证码尝试次数；
- 验证码日志不包含明文；
- Token TTL 数值；
- HTML 转义；
- 密码编码和校验；
- 空 Token 登出输入。

这些测试的价值是验证局部规则，但也要注意它们有些是“复制实现逻辑后测试模拟方法”，并不一定直接调用 Controller 或 Service。测试通过说明规则示例通过，不代表真实 HTTP 请求、Redis、数据库和文件系统都已经通过验证。

### 7.3 测试层次

```text
单元测试
  -> 纯逻辑、密码、输入校验、工具类

Web 层测试
  -> Controller 参数、状态码、鉴权和返回结构

集成测试
  -> Spring + MySQL + Redis + 文件系统

并发测试
  -> 秒杀库存、一人一单、锁竞争、重复请求

部署验证
  -> Nginx、网络、配置、真实依赖和回滚
```

当前仓库主要覆盖前两类中的局部内容，真实 Redis/MySQL 集成和秒杀并发证据仍需要后续补充。

### 7.4 测试用例设计方法

每个功能至少准备三类用例：

| 类型    | 示例                          |
| ----- | --------------------------- |
| 正常    | 合法用户登录、正常上传图片、库存充足下单        |
| 边界    | 空手机号、5 MB 边界、库存为 0、Token 过期 |
| 攻击/并发 | 路径穿越、恶意文件、XSS、重复下单、最后一件库存竞争 |

测试不应只断言“返回成功”，还应验证数据库和 Redis 的状态是否符合预期。

## 八、当前部署结构

### 8.1 Nginx 与 Spring Boot

当前 `nginx/conf/nginx.conf` 体现的部署关系是：

```text
浏览器
  -> Nginx:8080
       /       -> 前端静态文件
       /api/*  -> 去掉 /api 后代理到 127.0.0.1:8081
  -> Spring Boot
       -> MySQL
       -> Redis
```

Nginx 配置中包含安全响应头和 HTTPS 配置示例，但 HTTPS Server 块当前是注释状态。不能仅凭配置注释就说项目已启用 HTTPS。

### 8.2 当前部署边界

当前仓库没有看到 Dockerfile、Docker Compose、Maven Wrapper 或 CI/CD 工作流，因此可以确认：

- 仓库提供了 Nginx 配置和前端资源；
- 后端可以通过 Maven Spring Boot 插件构建；
- 没有形成容器化和自动化发布证据；
- 配置、MySQL、Redis、文件目录仍依赖部署机器的外部准备。

### 8.3 配置与环境差异

部署到另一台机器前至少要检查：

1. Java 版本是否满足 Java 8 配置；
2. MySQL 驱动、字符集和时区是否一致；
3. Redis 地址、密码和连接池是否正确；
4. 图片上传目录是否存在且应用用户有权限；
5. Nginx `/api` 代理路径是否和 Controller 路径一致；
6. 测试短信模式是否已关闭；
7. HTTPS 是否真正启用；
8. 日志目录、备份和回滚策略是否准备好。

### 8.4 部署验收不能只看首页

一次完整的部署验证至少应覆盖：

```text
进程启动
  -> 数据库连接
  -> Redis 连接
  -> Nginx 静态页面
  -> /api 路由代理
  -> 登录和 Token 续期
  -> 店铺缓存命中/回源
  -> 秒杀失败和成功路径
  -> 图片上传与删除权限
  -> 日志和错误响应
```

首页能打开只说明静态文件可访问，不能证明后端依赖、权限和业务链路正常。

## 九、安全与发布检查清单

### 安全

- [ ] 仓库和配置中没有真实密码、Token、验证码；
- [ ] 已提交过的真实凭据已经轮换；
- [ ] 生产模式不返回验证码明文；
- [ ] 上传不仅检查扩展名，还验证文件内容；
- [ ] 上传和删除接口都需要认证，并校验资源归属；
- [ ] Token、密码、验证码不会进入日志；
- [ ] 公开接口范围经过逐个确认；
- [ ] HTTPS 和安全响应头已在真实环境验证。

### 测试

- [ ] 单元测试通过；
- [ ] 应用上下文测试通过；
- [ ] MySQL/Redis 集成测试通过；
- [ ] 登录、缓存、上传、秒杀接口通过正常和异常用例；
- [ ] 并发测试验证库存和一人一单；
- [ ] 测试数据、临时文件和临时凭据已清理。

### 发布

- [ ] 构建产物来源明确；
- [ ] 配置通过环境变量或安全配置注入；
- [ ] 数据库备份和回滚方案明确；
- [ ] Nginx 代理和后端端口验证；
- [ ] 日志、监控和故障排查方式明确；
- [ ] 发布后做冒烟测试，而不是只检查进程是否存在。

## 十、阶段验收

不看代码回答：

1. 当前项目的登录认证在哪一层完成？授权是否已经细分？
2. 文件上传做了哪些防护？还缺什么？
3. 为什么测试类通过不代表真实环境验收通过？
4. Nginx 的 `/api` 代理如何映射到 Spring Boot？
5. 当前项目哪些部署能力有代码证据，哪些只是配置注释？
6. 如果发现配置中已经提交真实密码，正确处理顺序是什么？

阶段 6 的验收标准：你能用“攻击面—防护—测试证据—剩余风险”四句话描述一个安全问题，并能用“组件—依赖—验证—回滚”说明一次部署。
