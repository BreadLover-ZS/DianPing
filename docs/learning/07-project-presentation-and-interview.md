# DishReview 学习文档：阶段 7——项目表达与面试准备

> 本阶段不新增功能，目标是把已经读懂的代码讲清楚，并且能够面对面试官的连续追问。
>
> 前置阅读：阶段 0～6 全部学习文档。

## 一、项目表达的基本原则

项目面试不是背技术名词，而是证明三件事：

1. 你知道业务问题是什么；
2. 你理解自己写过或读过的代码为什么这样做；
3. 你能识别方案的边界，并知道如何验证和优化。

最危险的表达是：

```text
用了 Redis，所以性能很高；
用了分布式锁，所以不会超卖；
写了 Nginx 配置，所以已经生产部署；
有测试类，所以项目已经测试完毕。
```

这些说法都缺少具体链路和证据。正确表达应该包含：问题、方案、关键代码、验证方式和不足。

## 二、三种时长的项目介绍

### 2.1 30 秒版本

> DishReview 是一个基于 Spring Boot、MyBatis-Plus、MySQL 和 Redis 的餐饮点评平台，包含用户登录、店铺查询、探店博客、优惠券和秒杀下单等功能。项目中 Redis 主要用于验证码和 Token、店铺缓存、分布式锁以及订单 ID 生成。我重点熟悉了缓存穿透/击穿、逻辑过期、库存条件更新和一人一单等后端场景。

这段只负责建立全局印象，不要在 30 秒里塞进所有类名。

### 2.2 3 分钟版本

建议按以下顺序：

```text
项目定位
  -> 餐饮点评平台，主要业务模块

技术架构
  -> Spring Boot + MyBatis-Plus + MySQL + Redis + Nginx

核心链路
  -> 登录 Token
  -> 店铺缓存
  -> 秒杀下单

项目难点
  -> 缓存穿透/击穿、分布式锁、条件扣库存、事务代理

当前边界
  -> 部分社交功能尚未完整实现，秒杀和部署仍需更充分测试
```

### 2.3 10 分钟版本

10 分钟版本不能只是 3 分钟版本的重复，而应选择一条主线深入。推荐主线：

```text
用户登录建立身份
  -> 浏览店铺使用缓存
  -> 购买秒杀券产生并发
  -> Redis 和 MySQL 协同保证结果
  -> 安全、测试和部署保证系统可用
```

面试官打断时，应能够立刻跳到对应代码文件，而不是继续背稿。

## 三、项目亮点如何选择

当前项目适合讲的亮点有：

| 亮点 | 可以讲什么 | 不能夸大什么 |
|---|---|---|
| 店铺缓存 | 逻辑过期、异步重建、热点读取 | 没有压测不能说提升了多少 QPS |
| 登录会话 | Redis Hash、TTL、滑动续期、登出删除 | 不能说是完整 OAuth 或高安全认证 |
| 秒杀下单 | 用户锁、事务、条件扣库存、分布式 ID | 不能说已经验证了高并发不超卖 |
| 安全修复 | 上传、XSS、Token、验证码限制 | 测试局部通过不等于完整安全审计 |
| 数据库设计 | 金额整数化、表拆分、唯一索引思考 | 没有执行计划不能声称索引优化完成 |
| Nginx | 静态资源和 `/api` 反向代理 | HTTPS 注释配置不等于已启用 |

最好的项目亮点通常不是“用了最多技术”，而是你能连续回答：为什么、怎么做、怎么验证、有什么代价。

## 四、项目难点表达模板

### 4.1 缓存击穿

**问题：** 热点店铺缓存过期时，大量请求可能同时回源 MySQL。

**方案：** 项目使用逻辑过期，把数据和逻辑过期时间一起存入 Redis；过期后通过锁让一个线程异步重建，其余请求先返回旧数据。

**取舍：** 优点是请求不必等待重建，缺点是可能短时间返回旧数据，且需要考虑缓存预热、重建失败和锁释放。

**当前边界：** 当前入口确实使用了逻辑过期，但重建线程管理、锁释放原子性和时间单位仍需要继续验证。

### 4.2 一人一单与库存超卖

**问题：** 并发请求可能让同一用户重复下单，多个用户也可能同时竞争最后库存。

**方案：** Redis 锁按用户限制并发重复提交，事务内查询已有订单，数据库使用 `stock > 0` 条件更新扣减库存，再保存订单。

**取舍：** Redis 锁减少重复请求进入数据库，但不能替代数据库库存条件和唯一约束；当前还需要评估 `(user_id, voucher_id)` 唯一索引、Lua 原子解锁和并发测试。

### 4.3 Token 会话

**问题：** HTTP 请求本身无状态，需要在多次请求之间识别登录用户。

**方案：** Token 作为 Redis Hash 的 Key，保存脱敏的 UserDTO，并通过 TTL 和拦截器实现滑动过期；请求结束后清理 ThreadLocal。

**取舍：** Redis 适合共享会话，但 Token 泄露、TTL、日志脱敏和多设备策略仍需要安全治理。

## 五、按代码回答面试问题

### 5.1 架构问题

**问：项目为什么分 Controller、Service、Mapper？**

答题重点：Controller 处理 HTTP 边界，Service 编排业务、事务、Redis 和数据库，Mapper 负责持久化。分层让业务逻辑不直接堆在接口层，也便于后续测试和复用。

**问：一次店铺详情请求如何流转？**

答题顺序：Nginx `/api` 代理、拦截器、Controller、Service、Redis、MySQL 回源、缓存重建、Result 返回。

### 5.2 数据库问题

**问：为什么手机号要唯一索引？**

答：登录按手机号查询，唯一索引既优化查询，又从数据库层保证一个手机号只能对应一个用户。

**问：一人一单为什么还要数据库唯一约束？**

答：Redis 锁和 Java 查询都可能受锁过期、异常或并发边界影响，数据库唯一约束是最终一致性和正确性的兜底。当前项目需要继续评估并补齐这个约束。

**问：为什么金额用整数？**

答：以分为单位保存，避免浮点数计算误差。

### 5.3 Redis 问题

**问：缓存穿透和缓存击穿有什么区别？**

答：穿透是大量请求不存在的数据，导致不断查库；击穿是热点 Key 失效瞬间大量请求同时回源。项目分别提供空值缓存、互斥锁和逻辑过期等思路。

**问：逻辑过期为什么返回旧值？**

答：为了避免请求等待数据库重建，牺牲短时间数据新鲜度换取热点访问稳定性。

**问：分布式锁为什么要设置过期时间？**

答：防止持有锁的进程宕机后永久阻塞其他请求；但静态 TTL 过短会提前释放，过长会影响恢复，需要结合业务耗时和续期策略设计。

### 5.4 并发问题

**问：为什么不能先查库存再在 Java 中减一？**

答：多个线程可能读到相同库存，条件更新 `WHERE stock > 0` 让数据库在真正更新时再次判断，防止超卖。

**问：事务能不能保证 Redis 和 MySQL 一致？**

答：当前 Spring 事务主要管理 MySQL，Redis 锁和缓存不属于同一个本地事务，需要通过 TTL、重试、补偿和幂等策略处理跨组件不一致。

### 5.5 安全问题

**问：上传接口做了哪些安全防护？**

答：当前有登录拦截、大小限制、扩展名白名单、随机文件名和 canonical path 校验；但还应验证文件真实内容、资源归属、磁盘配额和生产目录配置。

**问：为什么测试通过不能证明安全问题已经解决？**

答：当前测试主要验证局部规则，未必覆盖真实 HTTP、Redis、MySQL、文件系统和并发场景；还需要集成测试、攻击用例和部署环境验证。

### 6.1 保守且真实的示例

```text
DishReview 餐饮点评平台
技术栈：Spring Boot、MyBatis-Plus、MySQL、Redis、Nginx

1. 实现手机号验证码/密码登录和 Redis Token 会话，使用 Hash 保存脱敏用户信息，结合 TTL 和拦截器实现登录状态续期。
2. 实现店铺详情缓存，结合空值缓存、逻辑过期和异步重建降低热点查询对 MySQL 的压力。
```

| 简历表述 | 代码证据 | 还需要什么证据 |

## 七、模拟面试顺序

### 第一轮：项目概览

1. 这个项目解决什么问题？
2. 你负责或重点学习了哪些模块？
3. 项目技术栈和整体架构是什么？
4. 选择一个你最熟悉的难点展开。

### 第二轮：代码追问

1. 店铺缓存从哪里读？未命中怎么办？
2. Token 为什么放 Redis？如何续期？
3. 秒杀为什么需要锁和事务？
4. `AopContext.currentProxy()` 为什么存在？
5. 数据库库存更新为什么使用条件语句？

### 第三轮：反向质疑

1. Redis 挂了怎么办？
2. 锁过期但业务还没结束怎么办？
3. 当前一人一单是否真的有数据库兜底？
4. 逻辑过期返回旧数据是否会造成业务错误？
5. 你的测试是否真的启动了 MySQL 和 Redis？
6. 你的 HTTPS 是否真正启用？
7. 配置文件中的默认凭据如何处理？

回答反向质疑时，不要急于证明项目完美。可以采用：

```text
当前实现是……
它解决了……
它没有解决……
如果继续完善，我会先验证……
```

这种回答比强行声称“不会有问题”更可信。

## 八、最终项目讲解稿

可以按照下面的模板自己写一版，不要直接照抄：

> 我介绍一下 DishReview，这是一个基于 Spring Boot、MyBatis-Plus、MySQL 和 Redis 的餐饮点评平台，主要包含用户、店铺、博客、优惠券和秒杀订单模块。整体上 Controller 接收请求，Service 编排业务，MyBatis-Plus 访问 MySQL，Redis 负责高频缓存、登录会话和并发控制。
>
> 我重点理解的是三条链路。登录时验证码和 Token 放在 Redis 中，并通过 TTL 和拦截器维护会话；店铺详情使用缓存，逻辑过期后通过锁异步重建；秒杀下单使用 Redis 用户锁限制重复请求，再通过数据库事务和 `stock > 0` 条件更新防止库存超卖，并用 Redis 自增生成订单号。
>
> 这些方案分别解决了缓存访问、登录状态和并发下单问题，但当前实现仍有边界，例如分布式锁释放还需要原子化，订单的一人一单需要数据库唯一约束进一步兜底，真实并发测试、集成测试和生产部署证据也需要继续补充。后续我会先围绕这些边界做验证，再进行优化。

这份讲解稿的价值不在于背下来，而在于每句话都能回到具体文件和具体数据流。

阶段 7 的验收标准：你能在不看稿的情况下讲清项目，并且面对追问时始终保持“代码事实—设计目的—验证证据—剩余风险”的逻辑。

## 十、后续优化的表达顺序

完成面试准备后，真正开始完善项目时，推荐按这个顺序表达和行动：

```text
先建立基线
  -> 当前测试、执行计划、接口行为、并发行为

再选择问题
  -> 只挑一个有证据的问题

再设计方案
  -> 说明为什么方案适合当前架构

再实现和验证
  -> 测试、日志、压测、异常和回滚

最后更新项目文档
  -> 写清改了什么、为什么改、结果如何、仍有什么风险
```

这样后续优化才会成为真正的项目经历，而不是只增加几个看起来高级的组件。
