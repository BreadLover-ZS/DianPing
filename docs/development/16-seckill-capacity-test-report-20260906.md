# 秒杀双机压测与容量边界报告（2026-09-06）

## 1. 结论

- 当前两台应用实例、隔离 MySQL/Redis/RabbitMQ 和压测机链路下，**300 QPS × 30 秒是本轮最高通过档位**：9,001/9,001 请求 HTTP 200、业务受理 100%、丢迭代 0，p95 16.73 ms。
- 500 QPS 未达到验收阈值：实际完成约 360 QPS，HTTP 失败 4.04%，丢迭代 93，最大耗时 28.43 秒。
- 1500 QPS 配置档未形成有效容量样本：仅完成 2,041 个请求，丢迭代 9,961，实际完成约 101.85 QPS，主要限制来自压测端 VU 和入口排队；目标机 CPU 约 5%～11%，未达到资源饱和状态。
- 测试结束后，券 11 的 37,177 个实际进入系统的事件全部收敛为 `status=2`，订单 37,177，`reservation_completed_at` 非空 37,177，Redis 预留结构清空，RabbitMQ 主队列和 DLQ 均为 0；两台应用恢复默认压测配置且健康检查为 UP。

综合本轮数据，**在当前双实例、单条 SSH 隧道入口和默认运行配置下，300 QPS 是 30 秒短时测试的最高通过档位，500 QPS 是已观察到的失败档位。** 由于尚未补测 350～450 QPS，也未执行 10 分钟以上稳定性测试，本轮结果不用于推导系统极限或长期稳定容量。

## 2. 测试范围与拓扑

- 压测机：AutoDL 第二台服务器，k6 2.2.0。
- 目标机：AutoDL 第一台服务器，应用实例 `6006`、`6008`，Java 8；MySQL、Redis、RabbitMQ 均为隔离实例/数据库/vhost。
- 到达路径：压测机 k6 → 压测机本地端口 → SSH 端口转发 → 目标机两个应用端口。该路径不是私网直连，结论包含 SSH 隧道入口的影响。
- 压测接口：`POST /voucher-order/seckill/{voucherId}`。
- 容量券：voucher 11，初始化库存和唯一令牌各 120,000；测试期间令牌区间不重复。早期一次 100 QPS 轮曾与 1500 QPS 档的飞行迭代重叠，已明确标记为无效并从结论排除。
- 被测 JAR SHA-256：`42fb9c55f63368f1ec4b10ef021b0f098ac1b143a729a916e4c9b3a1304e6884`。该哈希用于确认两个实例运行同一构建产物；本报告随修复代码一并提交，最终提交号以 Git 历史为准。

## 5. 本轮发现与修复

压测不仅验证入口速率，也暴露了积压条件下的收敛问题。本轮完成三项代码修复：

1. 消费事务提交后立即执行幂等 Redis 预留清理，并写入 `reservation_completed_at`；清理失败时保留空标记，由定时对账兜底，避免已成功订单长期堆积在待对账集合。
2. 对 `CONSUMED` 且完成标记为空的事件按 `consumed_at,event_id` 升序分批扫描，不再使用时间窗口截断，避免旧积压超过窗口后永久漏扫。
3. 将 `lease_owner` 从 64 字符扩展到 128 字符，覆盖“主机名 + 任务类型 + UUID”的实例标识长度，避免任务抢占时因字段截断失败。

相应消费者与对账分支已补充自动化测试。修复解决的是“成功订单的 Redis 预留最终清理”问题，不等同于已经完成 RabbitMQ 故障注入或多实例宕机恢复验证。

## 6. 资源观察

- 压测机 `vmstat`：CPU 大部分时间约 3%～6%，无 swap；未出现压测机 CPU 饱和。
- 目标机 `vmstat`：容量轮期间最高 CPU busy 约 13%，包含搜索/恢复阶段的采样最高约 16%，无 swap；1500 QPS 档并未把目标机 CPU 打满。
- 现有资源数据不足以将 500/1500 档的问题归因于 CPU，后续需要分别测量入口连接、Tomcat/连接池、同步数据库查询和 Outbox/Rabbit 发布吞吐。

## 8. 后续测试要求

- 在 350、400、450 QPS 档补测，收窄通过档与失败档之间的边界；每档至少重复 3 次。
- 对候选稳定档执行至少 10 分钟稳态测试，同时记录 P99、连接池、JVM、MySQL、Redis、RabbitMQ 和积压恢复时间。
- 使用私网直连或多条独立入口复测，拆分 SSH 隧道、压测端 VU 与应用本身的限制。
- 单独执行 RabbitMQ 中断、消费者宕机和恢复演练，验证默认配置下的积压恢复时延。

## 9. 结论适用范围

| 结论 | 证据范围 |
|---|---|
| 300 QPS 为本轮最高通过档位 | 双实例、单条 SSH 隧道、30 秒恒定到达率；HTTP 与业务受理均为 100%，无丢迭代 |
| 500 QPS 档未通过 | 实际完成约 360 QPS，HTTP 失败 4.04%，丢迭代 93，最大耗时 28.43 秒 |
| 已进入系统的请求最终收敛 | 37,177 个事件全部为 `CONSUMED`，订单数一致，Redis 预留与 RabbitMQ 队列无残留 |
| 1500 QPS 档不纳入服务容量判断 | 压测端出现大量丢迭代且目标机 CPU 未饱和，结果包含 VU 和 SSH 入口限制 |

本报告未覆盖生产网络、多节点数据库或消息队列、长时间稳态运行、RabbitMQ 故障注入及应用实例宕机恢复，因此不构成生产容量承诺或高可用验收结论。
